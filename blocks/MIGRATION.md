# Перенос блоков в папки (этап 5) — рабочий журнал

Решение заказчика 21.11: «Делай все блоки по плану и все проверь». Порядок — как в MODULAR_PLAN.md (от простых к сложным).

## Рецепт переноса одного блока

1. `blocks/<тип>/block.json` — вид, название, другие имена, Figma, меню (из `SLASH_GROUPS`), Markdown, клавиши, `html` (теги и атрибуты — убрать из базовых списков `src/core/allowlist.js` **и** `src/Sanitizer.php`, если ими пользуется только этот блок), `degrade`, `selector`.
2. `blocks/<тип>/<тип>.js` — `registerBlock({...json, match, create, clean, serialize, normalize, toText, isEmpty, fromJson})`. Функции **переносятся** из ядра, не переписываются (поведение то же).
3. `<тип>.editor.js` — правка внутри блока (бывший `src/ui/<x>.js`), подключается хуком `editor` реестра.
4. `<тип>.site.css` / `<тип>.editor.css` — правила из `styles/content.css` и `styles/ui/*.css`.
5. `<тип>.site.js` — поведение на сайте (из `src/site/content.js`).
6. `<Тип>.php` — превращение в текст на сервере (из `src/Presets.php`), если не `degrade: drop`.
7. `<тип>.test.js` — тесты: перенесённые прежние (`tests/<x>.test.js`) + свои.
8. Ядро не упоминает блок (тест набора `blocks`).
9. Проверки: `pwsh -File tools/test.ps1` (все наборы), `-Suite file:<x>` для ещё не перенесённых прежних тестов, снимок стилей `tools/css-snapshot.ps1` = контрольный `.css-base5.txt` (снят после переноса линии), Figma — сверка компонента, браузер.

## Итог 21.11

Три вида переноса (поле в `block.json`):

- **полностью** — ядро блок не упоминает (тест набора `blocks`): `hr`, `callout`, `background`;
- **текстовые** (`text: true`) — ввод, Enter, заглушки ведёт текстовый движок ядра; в папке описание, меню, «Стиль текста», клавиши, Markdown, JSON, наборы, стили, тесты: `p`, `heading`, `blockquote`, `pre`, `list`, `checklist`, `steps`, `facts`, `proscons`;
- **с модулями ядра** (`core: [файлы]`) — создание, окно настроек, правку, очистку и превращение в текст пока ведут модули ядра; тест сверяет, что каждый файл списка существует и упоминает блок. С 21.11 таких блоков нет: все десять отвязаны полностью (см. ниже); поле и тест оставлены для будущих блоков.

Найдено и исправлено по ходу (с тестами):

- Markdown «# », «- », «1. », «```» вставлял пустой блок вместо превращения абзаца, когда у текстового блока в реестре есть `create` (`editor.js`, тест — прежние «Markdown-сокращения»).
- Очистка считала блоком любой `<div>` / `<figure>`, как только в реестре появлялся `div.ted-button` или `figure.ted-iframe` — ломалась вставка картинок со страницы (`isBlockTag`: тег — блок только у селектора без класса; тест в `tests/blocks/registry.test.js`).
- Содержание на сайте — `<nav class="ted-toc">`, в правке — `<div>`: селектор `.ted-toc` (класс без тега), PHP `Blocks::of` понимает «.класс» (тесты в `tests/php/test-blocks.php` и `blocks/toc/toc.test.js`).
- Устаревшие проверки прежних тестов: имя кнопки × (`ted-ui-iconbtn` → `aria-label="Закрыть"`), команда `exec('hr')` → `exec('insert:hr')`, цвет нажатия «Открыть» — токен в правиле вместо вычисленного цвета, несуществующие классы `ted-ui-tableadd__btn`, `ted-ui-iconbtn`.

Поведение блоков на сайте — `blocks/<тип>/<тип>.site.js` через `siteBlock(fn)` (`src/site/blocks.js`): код (копирование), iFrame (высота), товар (корзина), таблица (прокрутка), вкладки, содержание.

Следующий шаг (не начат, нужен отдельный этап): отвязать ядро от блоков с `core` — точки подключения реестра (окно, клавиши, заглушки, очистка, превращение в текст JS и PHP, правила панели, действие после вставки), затем перенос `src/core/<x>.js`, `src/ui/<x>.js` в папки блоков.

## Отвязка ядра от блоков с модулями (с 21.11)

Решение заказчика 21.11: «Да, начинай». По одному блоку, после каждого — проверка заказчиком.

Точки подключения реестра (описаны в `src/core/registry.js`):

- `block.json`: `toolbar` { bg, align, style: false; marks: [разрешённые] }, `neverEmpty`, `caretBelow`;
